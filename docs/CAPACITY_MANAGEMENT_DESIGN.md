# forkfs 产品规划：本地工作空间、远程备份与集群管理

状态：产品规划草案，待 review。为保持 PR #6 的链接连续性，保留原文件名。
本文描述目标与分期，不是已实现能力或已确定的技术方案。本 PR 仅修改文档。

## 1. 产品定位

forkfs 为开发者及多 Agent 工作流提供可以快速创建、保留和清理的独立工作空间。
用户无需理解底层存储细节，就能知道：

- 工作空间最多可以占多少本地磁盘。
- 当前用了多少、什么时候需要清理、哪些内容可以安全清理。
- 哪些重要版本已备份，以及本机丢失或损坏后如何恢复。
- 多台机器上有哪些工作空间、各节点是否健康，以及任务在哪台机器执行。
- 一个 World 或版本具体改了什么，是否值得保留、备份或交给他人审阅。

核心体验是 **本地容量可控、清理有依据、重要版本可恢复**。
先完善 macOS 本地使用闭环，再扩展远程备份与多机器统一管理，
不把集群管理等同于分布式共享文件系统或多人实时协作。

## 2. 基础功能与付费功能

| 范围 | 产品能力 | 定位 |
| --- | --- | --- |
| 本地工作空间 | 初始化、fork、checkpoint、查看与管理 | 基础功能 |
| 内置 Git 集成 | 仓库识别、独立分支、基线记录、工作区生命周期 | 规划中的基础功能，跟踪 [Issue #7](https://github.com/forks-world/forkfs/issues/7) |
| 本地容量管理 | 初始化总容量、用量展示、接近上限提醒 | 基础功能 |
| 安全清理 | 清理预览、垃圾状态、用户主动回收 | 基础功能 |
| 本地差异审阅 | 文件变化、版本间比较、逐行文本 diff 与 patch 导出 | 基础功能，已有文件级能力，其他待实现 |
| 本地安全合并 | 合并预览、共同基线三方合并、冲突处理与独立结果 World | 规划中的基础功能，尚未实现 |
| 远程备份 | 上传选定版本、计划备份、备份历史 | 付费功能 |
| 远程恢复 | 查找恢复点、下载并恢复到本机或新设备 | 付费服务的一部分，已有数据取回不以续费为条件 |
| 远程权限与审计 | 租户/项目隔离、角色授权、凭证撤销、敏感操作记录 | 远程备份和集群的必备安全能力，不额外收费解锁基本保护 |
| 集群版 | 节点接入、统一状态、工作空间目录、远程管理与任务跟踪 | 独立产品形态，是否付费及如何打包待确认 |

本地核心功能不要求登录或联网。远程备份必须显式启用，不默认上传用户数据。
具体套餐、价格、远端空间额度与超额规则留待后续商业设计。

## 3. 首次使用：先确定空间边界

用户初始化时选择源项目及分配给 forkfs 的总容量。产品说明这是什么限制、
首次导入是否需要复制、需要哪些权限，再让用户确认，不悄悄改变磁盘布局。
初始化结束后，用户直接进入创建与使用 World 的流程。

按用户 review 意见，**优先实现物理空间硬上限**，而不是只做逻辑软预算。
目标是由文件系统限制受管工作空间继续分配空间，而不只在 forkfs 命令里提醒。
当前优先评估专用 APFS 卷配额；它可能要求全部受管 World 位于指定存储区域。
实现方式、权限和兼容性在后续技术设计验证，若不可行再明确讨论替代方案，
不能静默降级成软限制。

容量上限不等于预留空间：宿主磁盘仍可能被其他应用占满。产品须同时展示
forkfs 容量与宿主可用空间。旧的普通目录模式不被自动迁移，也不能被标为
已经具有硬配额保护。扩容、迁移和存储区域退出流程后续单独设计。

## 4. 日常使用：看得懂的状态与提醒

用户能快速看到总容量、当前占用、可用空间和是否需要采取行动。不把克隆的
逻辑大小简单相加并冒充物理占用；指标暂不可用时明确说明，不显示虚假健康状态。

初步提醒建议：

- 低于 80%：正常展示。
- 达到 80%：建议查看可清理内容。
- 达到 95%：强调空间紧张，建议尽快清理。
- 达到限制或实际空间不足：说明写入失败原因及可行的恢复步骤。

阈值待使用反馈调整。第一阶段在 CLI 使用过程中展示提醒，不承诺常驻后台
实时通知；即便用户不运行 CLI，硬容量限制仍应由底层执行。后续是否增加
菜单栏或桌面通知取决于实际需求。

## 5. 清理体验：先说明，再执行

接近容量时提供清晰的下一步，而不是只打印“请运行 GC”：

1. 预览已到期垃圾、暂不能回收的对象及原因。
2. 有可回收内容时，由用户主动启动清理，并展示进度与结果。
3. 主要占用来自活跃 World、快照或预热池时，引导用户选择不再需要的内容。
4. 没有安全清理对象时明确说明，不能暗示 GC 一定能解决。

不自动删除活跃工作，不为腾空间缩短保留期，不承诺预览字节等于实际释放量。
容量已满时仍应提供可理解的恢复流程，不能陷入“需要清理但无法清理”的死角。

Codex review 指出的约束保留为后续设计门槛：**清理预览必须真正只读**。
当前普通 store 打开可能触发恢复和写入，不能直接复用后宣称零修改；技术方案
必须解决这一点，或明确报告无法安全预览，不偷偷执行恢复。

## 6. 付费远程备份：保护重要版本

### 用户体验

用户开通付费服务后，明确选择要备份的项目或快照，看到上传进度、远端用量、
最近成功恢复点及失败原因。第一阶段以已提交快照为备份单位，不把仍在修改
的 World 默认为已备份，也不暗示所有实时修改都得到保护。

先提供手动备份与完整恢复，再增加计划备份、历史保留和配额提醒。建议优先
评估托管远端，减少配置负担；自带对象存储、团队共享及多区域策略后续再评估。

### 恢复与信任

- 能从备份恢复到新目录或新设备，不默认覆盖已有工作。
- 明确展示“可恢复的版本”，不能把上传请求成功当作备份完成。
- 备份默认不触发本地删除，恢复也不得绕过本地容量限制。
- 加密传输与存储，明确密钥管理及恢复方式；具体安全方案单独设计和 review。
- 不上传未经用户选择的数据，不用备份内容训练或进行与备份无关的处理。

### 付费边界

本地容量和远端备份额度分开展示。远端额度不足时暂停新上传并提示，不默认
产生超额账单或自动升级。价格、计费口径、区域选择与保留期限尚未确定。

到期或取消订阅不影响本地工作；对于仍在约定保留期内的已有备份，允许查看、
下载和恢复，但仍须具备有效的数据访问权限，不以续费作为取回数据的条件。
成员移除或权限撤销不能因“到期可取回”而被绕过。保留期及到期删除规则必须购买前
说明并提前通知，不能在本文里擅自设定自动删除期限。

## 7. 集群版：多机器统一管理

### 用户场景与首期范围

面向拥有多台开发机、Mac 节点或 Agent 执行机器的个人与团队，提供一个统一
入口，回答“机器是否在线、空间是否充足、工作空间在哪里、操作是否完成”。
首期支持同一管理域内的 macOS 节点，不因此承诺 Linux/Windows 支持。

- **节点管理**：显式加入、命名/标签、查看版本与健康状态、撤销接入。
- **统一视图**：按节点查看容量、World、快照、备份状态及最近更新时间，
  可以筛选项目与节点，不必逐台登录查看。
- **远程管理**：选择明确节点发起创建工作空间、checkpoint、备份或安全
  清理，跟踪排队、执行、成功、失败与待确认状态；不默认提供任意远程 shell。
- **跨机器恢复**：把已提交的快照通过明确的数据传输或备份恢复到另一节点，
  先检查目标容量及权限；恢复完成不自动删除源数据。

首期由用户选择目标节点；自动调度、负载均衡和自动故障迁移后续再评估。
集群管理不强制所有数据上传云端；节点间传输与付费远程备份的权益边界单独
确认，不把跨机恢复默认为已购买云备份。

### 必须明确的边界

每个节点仍独立存储、独立执行本地硬配额。集群汇总容量只是管理视图，不能
把 A 机器的剩余空间直接用于 B 的写入，也不承诺跨机器 fork 与本地克隆同速。
同一 World 不在多台机器同时共享可写状态；实时同步、共享文件系统和冲突
合并不属于本期集群版。

管理服务或网络不可用时，已有本地工作继续；离线节点显示离线/数据过期，
不显示健康，也不能把未收到结果的远程任务判为成功或自动重复执行。重连后
应核对任务实际状态，避免重复创建或重复清理。

统一管理必须包含最基本的节点认证、访问范围控制和操作记录；不能以首期
功能少为由省略。删除、GC 等操作明确显示目标节点与对象，支持先预览，
遵守节点本地依赖和保留策略。撤销节点接入停止新的远程控制，不擦除本地数据。
复杂企业权限、SSO、跨组织管理和控制服务高可用另行规划。

### 产品形态与商业边界

“集群版”先作为独立产品形态纳入路线图。托管控制服务还是私有部署、按节点
还是按团队收费、是否与远程备份套餐组合，均待确认；目前只有远程备份明确
为付费功能，不据此直接认定所有多机管理都付费。即便组合销售，也须分别
展示节点管理权益和远端存储额度。

## 8. 内置 Git 集成与选择性产物管理

需求跟踪：[Issue #7：World 内置 Git 集成](https://github.com/forks-world/forkfs/issues/7)。
本节记录产品方向，具体实现选择与验收细节继续在该 issue 跟踪，尚未实现。

World 是任务工作区，不强制等同于 Git worktree；但检测到 Git 仓库时，
Git 集成应内置，不能把普通目录克隆误报为已经创建 Git 分支。

- 非 Git 目录继续使用普通 World，无需账号或 Git 仓库。
- Git 仓库默认通过一次 fork 创建 Git 集成 World，建立独立分支并记录
  基线 commit，不要求用户另行手动执行 worktree add。
- 已有 worktree 必须识别其管理目录关系，不能直接复制 `.git` 指针并复用
  原工作区状态。原生 worktree 或独立 Git 管理目录的选择留待技术验证。
- 存在未提交修改时，明确选择从已提交版本创建，或携带当前修改；说明
  暂存、未暂存、未跟踪与忽略文件的处理，不静默提交或丢弃用户工作。
- 未跟踪的大文件仍按 forkfs 克隆及用户声明策略处理，不因 Git 集成而遗漏。
- checkout、commit、discard、restore、GC 不得意外损坏其他 World；若共享
  refs 或对象库，必须明确共享边界。源码基线与文件系统快照分别标识，
  不能把一次 checkpoint 自动等同于 Git commit。

文件生命周期也应按用户意图管理，而不是默认给整个目录建立长期版本：

| 内容 | 职责与策略 |
| --- | --- |
| 源码 | Git 管理提交、父子关系、文本 diff 与 merge |
| 显式发布的数据、模型或交付产物 | 产物管理记录不可变版本、确切输入依赖及保留/备份策略 |
| 用户声明可重建的中间产物 | 记录输入和生成方式，内容可按明确策略回收 |
| 用户声明的缓存、临时文件 | 默认不纳入长期产物版本及自动备份，可按已批准策略清理 |
| 未分类文件 | 不自动长期版本化，也不擅自删除或上传 |

通过配置清单、CLI 或 Agent/API 声明路径、产物版本和依赖，具体接口另行
设计。不能按扩展名推断文件可丢弃；原始数据可能不可重建。版本父子关系
用于比较/合并，输入依赖用于追溯/重建，两者不能混作共同基线。

全量文件系统快照仍可用于短期隔离和恢复，但不是所有内容都应长期保留。
远程备份范围需与用户选择一致：整快照备份须明确选择并告知包含范围，
选择性产物备份则需独立完整的清单及恢复语义，不能上传整树冒充只备份产物。

## 9. 差异查看与审阅

### 已实现的基础能力

当前 `world fs diff W1` 比较 World 与其记录的基线快照，输出新增、修改、
删除及仅元数据变化的文件；`--stat` 提供汇总。比较涉及文件内容及权限、
xattr 等元数据，已有专门的 diff 测试。参见 [使用说明](../README.md#world-fs-diff)
和 [CLI 实现](../cli/main.cpp)。这些是文件级变化清单，不是逐行文本 diff，
也不是任意两个版本之间的通用比较。

### 目标体验与分期

用户在 checkpoint、备份、清理或交付 Agent 工作成果前，能看懂改动，选择
需要保留的版本，并向他人提供可审阅的结果。

- **本地优先**：支持选择两个 World / 快照进行比较，明确显示双方身份与
  基线；提供目录/文件摘要、逐行文本差异及常规文本 patch 导出。
- **展示增强**：在基础比较稳定后，再评估可视化或外部 diff 工具集成，
  不把图形界面作为首个版本的前置条件。
- **跨机器扩展**：集群版后续支持选择不同节点上的版本或远端恢复点比较，
  明确权限、数据获取范围、传输进度与成本；不能因为已有集群总览就宣称
  已能读取和比较所有节点内容，也不默认上传文件。

### 范围与可信度

差异查看默认不修改比较对象。正在被写入的 World 不保证比较期间内容固定，
应提示结果可能变化；需要可复现审阅时引导使用已提交快照。读取失败或内容
不可用必须明确呈现，不能把“未能比较”显示为“没有变化”。

二进制、大文件、符号链接及权限/xattr 变化采用适合的摘要，不强行显示文本
行差异。patch 导出首期只覆盖明确支持的文本变更，不承诺完整保存权限、
xattr、硬链接或全部文件系统语义；不支持的变化必须列出，避免误以为 patch
能够完整还原一个 World。安全合并按下一节独立交付，不因提供 diff 就宣称
已有 merge 能力；任意 patch 的自动应用不包含在 diff 导出承诺中。

本地 diff 与文本审阅属于基础功能，不要求远程订阅；跨节点查看的管理权益
待集群版方案确认，访问远端备份仍遵守数据取回原则。

## 10. Safe merge：安全汇总分支成果

### 目标体验

多个 Agent 或开发任务从同一版本创建 World 后，用户可以审阅并汇总成果，
不必手工复制文件，也不用担心合并直接覆盖原工作。safe merge 是规划中的
新能力，不是现有 diff 的隐含功能。首期支持本地、一次两个分支的显式合并，
不承诺任意数量分支自动汇总。

源码优先使用 Git 的基线、diff 和合并语义，与 [Issue #7](https://github.com/forks-world/forkfs/issues/7)
的内置集成一起设计。用户显式发布的产物按版本选择或专门策略处理，临时文件
和缓存不默认参与；不承诺对整个工作目录做通用自动合并。非 Git 内容没有
可靠版本血缘时只支持查看差异或显式选择版本，不能伪装为安全三方合并。

建议流程：**选择版本 → 查看合并预览 → 处理冲突 → 生成独立结果 World →
用户验证后采用**。本地 safe merge 归入基础功能，不依赖付费备份。

### “Safe”的产品承诺

- **有可靠共同基线**：源码以双方 Git commit 及其共同祖先进行三方比较；
  其他支持合并的内容必须有独立、可靠的版本基线。未提交工作须显式处理，
  不能用文件系统 checkpoint 代替 Git 提交，也不边写边合并。
  基线缺失、历史关系不明或存在多个无法
  判定的基线时停止并解释，不猜测，不降级成覆盖式目录同步。保留可验证的
  版本血缘是技术设计前置条件，不能假定当前记录已经足够。
- **先预览、不动原件**：预览列出可合并变更、冲突、未支持项和输入版本；
  执行绑定这些不可变输入，不因源 World 后来改变而偷偷换版本。原始 World
  和快照不被修改，合并在隔离的结果区域进行。
- **冲突不静默覆盖**：普通文本中可以可靠合并的修改自动处理；双方冲突、
  删除与修改、路径/类型冲突等交由用户选择或编辑。不默认“后写覆盖前写”，
  未解决的结果不能标为完成；若提供冲突草稿，须明确区分草稿与完成结果。
- **不能处理就说明**：二进制、数据库、大文件、符号链接、权限/xattr、
  硬链接及重命名等分别定义支持范围。无法可靠处理时标为冲突或不支持，
  不丢弃元数据、不跟随链接向结果区域外写入，也不依靠模糊猜测合并重命名。
- **结果可放弃、过程可恢复**：通过校验后才发布新的结果 World，保留输入
  与基线记录供追溯。取消、磁盘满或进程中断不破坏输入，不把半成品报告为
  成功；容量限制和 GC 对正在使用的输入、结果的保护仍需遵守。

“安全”意味着不悄悄损坏或覆盖原工作，**不保证合并后的程序逻辑正确**。
即使没有文本冲突，也应提示用户运行项目测试并审阅结果；不自动执行输入
内容携带的脚本。第一期不原地替换目标 World，不自动部署或推送合并结果。

### 分期与边界

先完成本地两分支合并闭环与故障恢复，再考虑集群节点上的成果汇总；跨节点
需先把有权限访问的不可变版本及共同基线可靠获取到执行节点，不能把远程
活跃目录直接视为稳定输入。远程传输不自动开启，耗时与空间需求须可见。

验收重点是：能合并互不冲突的修改；冲突和不支持项不误报成功；用户可以
解决冲突后得到独立结果；取消、失败和重试不改变原件。实时多人编辑、自动
业务语义冲突解决、多分支自动调度与原地应用不属于首期。

## 11. 对象存储与集群权限管理

### 产品原则与资源边界

备份进入对象存储后，权限管理必须与远程功能一起交付，不能等到企业版再补。
登录身份、数据访问权限和付费权益是三件不同的事：付款不等于有权读取所有
备份，有权恢复已有数据也不要求订阅仍有效。个人用户默认拥有独立空间，
团队以组织/项目划分资源，默认私有、默认拒绝，未经授权不可枚举他人资源。

授权对象包括项目、备份集合/恢复点、已发布产物以及集群节点。列表、搜索、
文件名、manifest、diff 内容和下载链接同样属于受保护数据，不能只保护文件
正文。首期以项目/备份集合级授权为主，不提供复杂逐文件 ACL 或跨组织共享。

### 初步角色与动作

| 角色 | 默认职责 | 不默认拥有的能力 |
| --- | --- | --- |
| 所有者/权限管理员 | 成员、角色、项目授权与服务凭证管理 | 不应因管理账单自动获得数据读取权；管理员自授权须显式且可审计 |
| 备份写入者/节点服务身份 | 向指定项目创建备份并查询自身任务状态 | 下载已有备份、删除历史、变更权限或保留策略 |
| 恢复读取者 | 浏览获授权的备份并下载/恢复 | 上传、删除、修改保留策略或授权他人 |
| 数据维护者 | 在授权范围内管理备份保留和删除 | 管理组织成员或读取其他项目 |

个人空间创建者可同时拥有这些角色；团队场景允许拆分。具体角色名称后续可
简化，但查看内容、创建备份、恢复、删除、管理权限须为可区分的动作。
付费/账单管理员独立于数据角色；支持人员不得默认获得客户内容访问权限。

跨节点恢复需同时具备源备份读取权和目标节点/项目写入权；远程 diff/merge
也检查每个输入及输出位置的权限。节点加入集群不自动获得全部项目的备份
下载或删除权限，单个节点凭证泄露的影响应被限制在其授权范围内。

### 对象存储访问与凭证

用户通过产品授权访问备份，不向所有客户端发放共享 bucket 管理密钥。存储
默认不公开，服务端逐请求验证身份、项目和动作，并在存储访问层落实对应
边界；不能仅依赖难猜的对象 ID 或客户端隐藏按钮。客户端获得的上传/下载
能力应短时、最小范围，不能任意列举或读写整个 bucket。

访问凭证支持过期、轮换和撤销，不写入普通日志或备份内容。若采用签名链接
或临时存储凭证，需明确有效窗口和撤销限制；不能声称撤权可追回已下载数据，
也不能承诺所有已签发链接瞬时失效。首期不开放匿名公共分享链接。

本地文件权限与云端权限分开管理：上传不会自动把本机用户/组映射为团队
成员，恢复时不因备份内权限元数据授予额外系统权限。加密与授权也分开设计：
有密钥不应绕过服务端访问控制，拥有管理角色也不代表能解密端到端加密内容。
团队密钥分发、成员离开后的访问边界和恢复密钥流程须在开放团队备份前明确。

### 删除、撤权与审计

删除备份、缩短保留期、变更权限和导出凭证属于敏感操作，要求相应授权及
明确确认。删除权限不能绕过已约定的保留锁；长期凭证默认不给节点永久删除
能力。账户到期与成员离职是不同事件：前者遵守数据取回规则，后者停止其
后续受保护访问；正在进行的任务在关键授权点重验，不能无限沿用旧权限。

记录操作者/服务身份、项目、对象、动作、时间和结果，覆盖授权变更、备份、
恢复/下载授权、删除和失败访问；不记录明文密钥或文件正文。审计记录由受限
入口管理，普通节点和数据维护者不能随意修改或删除；保留期另行确定。

### 首期验收门槛

远程 MVP 上线前须验证跨租户/项目越权被拒、列表与内容权限一致、写入身份
不能删历史、凭证过期/撤销、成员移除、到期仍可合法取回、跨节点双向授权、
保留约束及敏感操作审计。SSO、复杂自定义角色、审批流及企业合规认证后续
评估，不影响首期必须具备的隔离和基本访问控制。本文只规定产品要求，
具体对象存储供应商、IAM 和密钥方案留待独立安全设计与 review。

## 12. 交付阶段与完成标准

| 阶段 | 核心范围 | 完成标准 |
| --- | --- | --- |
| P1 本地容量闭环 | 初始化硬容量、状态、提醒、安全 GC 引导 | 用户可以设定边界、看懂占用并安全处理空间不足 |
| P1a 内置 Git 集成 | 仓库识别、独立分支、基线与修改处理；[Issue #7](https://github.com/forks-world/forkfs/issues/7) | 一次 fork 获得明确 Git 身份，不误用原 worktree，不损坏用户修改或其他 World |
| P1b 本地差异审阅 | 任意 World/快照对比、逐行文本 diff、文本 patch 导出 | 用户能识别改动并导出支持范围内的审阅结果，无法比较的内容不误报一致 |
| P1c 本地 safe merge | 共同基线、合并预览、冲突处理、独立结果 World | 不修改输入，冲突不误报成功，失败可恢复；用户验证后再采用结果 |
| P2 付费备份 MVP | 显式启用、手动备份与恢复、权益校验、租户/项目隔离、基础角色及审计 | 完成恢复闭环，同时通过越权、撤权和合法取回验证 |
| P3 日常备份体验 | 计划备份、失败提示、保留策略、额度管理 | 用户能持续了解保护状态，且不会意外收费或失去取回渠道 |
| P4 集群管理 MVP | 节点接入、统一视图、指定节点操作、基础权限与操作记录 | 至少两台机器可统一管理，断连/重连时状态可信且不重复执行操作 |
| P5 跨节点工作流 | 快照分发/恢复、跨节点比较与成果合并、容量检查及传输状态 | 用户能比较、恢复或合并选定不可变版本，不覆盖已有工作或删除源数据 |

以上是建议顺序，暂不承诺日期。集群统一视图与管理本身不依赖付费备份，
可根据多机需求优先级提前；跨节点工作流可复用后续快照传输/恢复能力。
Git 集成、本地差异审阅和 safe merge 不依赖备份或集群服务，可作为独立迭代；
源码 safe merge 以内置 Git 集成和差异审阅为前置。产物版本与依赖声明在
选择性备份和跨节点产物分发前单独设计验收，可视化展示另行排期。
每阶段先有独立技术设计与验收，再开始实现；不把 P1 的本地功能依赖于账号、
支付或远程服务上线。

暂不纳入：自动淘汰用户工作、实时云同步、实时多人协同编辑、跨平台完整支持、
复杂企业权限体系、存量数据无感迁移、分布式共享文件系统和自动任务调度。
远程备份与集群的基础访问控制、租户隔离和审计不在排除范围，也不能推迟到
企业版。后续基于用户需求再排优先级。

## 13. 下一轮需要确认的事项

- 是否接受硬配额可能带来的指定存储区域、首次复制和权限确认。
- 是否认可以本地闭环 → 手动付费备份与恢复 → 计划备份的顺序交付。
- 远程服务是否优先托管，而非先支持用户自带 bucket。
- 集群版是否需要优先于计划备份；首先服务个人多机还是团队共享节点。
- 集群控制服务的托管/私有部署选择，以及独立收费或套餐组合方式。
- 本地差异审阅与容量管理的优先级，以及是否先完成 CLI 再做可视化。
- safe merge 是否按本地两分支、独立结果 World 优先交付，原地应用后续再评估。
- Git 集成与产物管理的职责边界；具体 Git 工作区布局继续在 Issue #7 验证。
- 远程权限是否以项目/备份集合为首期粒度，以及团队角色与密钥管理的范围。
- 套餐、价格、远端额度、保留期和具体技术路线另开设计，不在本轮定死。

已确认方向：硬上限优先；安全预览不能改数据；远程备份属于付费功能；
增加集群版，支持多机器统一管理；在已有文件级 diff 上补齐差异审阅与
safe merge，明确它们尚未实现的部分和安全边界。
内置 Git 集成按 [Issue #7](https://github.com/forks-world/forkfs/issues/7) 跟踪，
源码版本与用户显式声明的产物版本分开管理。
远程备份与集群必须同时具备基础权限管理，不能只提供存储上传能力。
本轮只 review 产品范围和优先级，不代表底层能力已验证或已批准实现方案。
