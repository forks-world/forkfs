# forkfs 产品规划：本地工作空间、远程备份与集群管理

状态：产品规划草案，待 review。为保持 PR #6 的链接连续性，保留原文件名。
本文描述目标与分期，不是已实现能力或已确定的技术方案。本 PR 仅修改文档。

## 1. 产品定位

forkfs 为开发者及多 Agent 工作流提供可以快速创建、保留和清理的独立工作空间。
用户无需理解底层存储细节，就能知道：

- 工作空间最多可以占多少本地磁盘。
- 当前用了多少、什么时候需要清理、哪些内容可以安全清理。
- 哪些重要版本已备份，以及本机丢失或损坏后如何恢复。
- 多台机器上有哪些工作空间、各节点是否健康，以及任务在哪台机器执行。
- 一个 World 或版本具体改了什么，是否值得保留、备份或交给他人审阅。

核心体验是 **本地容量可控、清理有依据、重要版本可恢复**。
先完善 macOS 本地使用闭环，再扩展远程备份与多机器统一管理，
不把集群管理等同于分布式共享文件系统或多人实时协作。

### 现状基线（已实现，macOS）

规划从下列已有能力出发，详见 [README](../README.md) 与
[macOS 验证说明](MACOS_VALIDATION.md)；本文其余部分除非注明“已实现”，均为规划。

- `world fs init / fork / checkpoint / list / inspect / verify`：快照与 World 的
  生命周期；World 位于用户指定的任意路径。原生克隆要求 World 与 store、源项目
  在同一 APFS 卷，因为 `clonefile()` 不能跨卷；`fork --copy` 是已支持的显式例外，
  它在其他卷上做逐文件的真实复制，没有克隆的速度与空间共享。
- `discard / restore / gc`：先进 trash、保留期后由后台回收；`gc --status` 查看
  垃圾与回收进度；预热池 `pool fill / status / drain`。
- `world fs status`：store 位置、对象计数与所在卷的剩余空间。**没有任何容量上限**，
  也不区分 forkfs 占用与宿主其他占用。
- `world fs diff`：World 相对其基线快照的文件级变化（见第 9 节）。
- 磁盘满行为：克隆前的空间准入检查，以及在受限 APFS 映像内验证过的
  `ENOSPC` 行为，即失败的操作不发布半成品、释放空间后可继续使用。

因此 P1 要补的是：上限、占用归因、提醒与清理引导，而不是重做生命周期。

## 3. 首次使用：先确定空间边界

用户初始化时选择源项目及分配给 forkfs 的总容量。产品说明这是什么限制、
首次导入是否需要复制、需要哪些权限，再让用户确认，不悄悄改变磁盘布局。
初始化结束后，用户直接进入创建与使用 World 的流程。

按用户 review 意见，**优先实现物理空间硬上限**，而不是只做逻辑软预算。
目标是由文件系统限制受管工作空间继续分配空间，而不只在 forkfs 命令里提醒。

### 可行性：已实测，初步成立

针对 PR 上“能实现物理上限么”的问题，已在隔离的磁盘映像内实测带配额的专用
APFS 卷，完整记录见 [可行性实测](CAPACITY_QUOTA_FEASIBILITY.md)。要点：

- 上限由文件系统执行，forkfs 不运行时同样有效；普通用户即可创建，无需 sudo。
- 配额按物理字节计费：整树克隆每次只占约 100 KB，修改多少才计多少。
  用户设定的容量因此就是真实磁盘占用，不需要换算逻辑大小。
- 配额不预占空间，未用部分仍归宿主磁盘上的其他应用使用。

尚未验证的是内置磁盘容器：普通用户能否在其上添加卷、是否需要认证、
Time Machine 本地快照是否会让已删除的空间暂不返回。这是 P1 技术设计的第一项
验证。**只有这项验证失败，才按用户意见回头讨论软上限**，并且届时明确标注为
软限制，不静默降级。

### 硬上限带来的产品后果

实测同时确定了下面几条，它们是采用硬上限的代价，须在初始化时向用户说明：

- **受管存储区域是一个专用卷**。`clonefile()` 不能跨卷，同一容器内也不行，
  所以源项目的基线、store 和所有 World 都必须位于该卷内。
- **首次导入是一次完整复制**，耗时与占用取决于项目内容，并计入容量。
  导入前展示预计大小与剩余容量；原项目目录保持不动。预估不能直接取源目录
  当前的物理占用：源项目里若已有 APFS 克隆出来的文件，例如用克隆方式复制的
  依赖或数据集，它们在源卷上共享数据块，跨卷复制后各占一份，1 GB 的源可能
  在受管卷上变成几十 GB。导入与扩容适用同一条要求：尽量按克隆关系重建，
  相同内容只复制一次、其余在受管卷内克隆；做不到时，按目的端的保守上界来
  预检，并把“源上占用”和“导入后预计占用”分开展示，差距明显时提醒用户，
  预计放不下则不开始。这个上界不只是各文件逻辑大小之和：还要计入每个条目的
  inode 与目录开销，实测约每条目数百字节，大量空文件和小文件的项目尤其明显；
  xattr 与 ACL 的占用；分配取整；导入自身的暂存与清单；以及实测中配额尾部
  数 MB 写不进去的余量和第 5 节要求的控制面余量。预检是估算而不是保证，
  估算偏小时由下一条的失败可回滚来兜底；两者缺一不可。
- **导入要么完成，要么不留下负担**。预估偏小、宿主同时被占满或用户取消，
  都可能让导入停在半途，留下一棵占着新卷的半成品树，甚至恰好写到上限，
  而第 5 节已经说明上限处普通命令全部失效。导入中的树须有明确标记，任何
  时候都不会被当成可用的项目或快照；中断或空间不足时自动回滚，或由产品
  提供只依赖删除的清理与重试入口，不需要用户到 forkfs 之外手工处理，也不
  需要先腾出空间才能清理。原项目始终不受影响。
- **导入范围止于所选项目自己的文件系统**。项目目录里可能挂载着外部卷或网络
  共享，它们看起来只是普通目录，符号链接检查发现不了。导入须递归识别挂载点
  和文件系统边界，默认不越过，并与卷外符号链接一样列给用户，由用户选择排除、
  明确纳入或中止；不把无关或敏感的外部数据当作项目的一部分复制进来，也不让
  它们意外占满容量。
- **导入结果必须与源一致**。受管卷里的副本是此后所有快照和 World 的来源，
  原目录保持不动反而会掩盖副本的损坏。导入完成前按第 11 节统一定义的保真范围
  核对副本与源。硬链接还有一种跨卷复制必然保不住的情形：项目里的文件与所选
  目录之外的某个名字是同一个文件。复制之后两者不再相连，在受管副本里的修改
  不会再反映到外部那个名字上，而只比较树内可见的硬链接组会让导入看起来完全
  一致。现有 `init` 已经能发现并警告这种情况，P1 导入器须保留这项检测，
  列出受影响的路径并要求用户明确确认或中止，不把这样的副本报告为完全一致。
  无法保留的条目逐项列出；出现这种情况时中止导入，或明确把导入标为不完整
  并由用户决定是否继续，不把只保住字节的副本报告为成功。
- **导入的是一个稳定的源，不是一个正在变化的目录**。复制耗时与项目大小成正比，
  期间源项目若仍在被编辑或构建，逐项核对只能证明每个文件在被检查的那一刻
  一致，不能证明副本对应任何一个完整的时间点。导入必须从稳定的源进行：
  先在源所在卷上取得一份不再变化的副本再复制，或要求用户确认源已静止，
  并在复制结束时检测整棵树在此期间是否发生变化。检测到变化时重新导入或
  拒绝，不把混合了不同时刻内容的副本报告为成功。具体手段由技术设计选择。
- **链接式 Git worktree 不能被原样复制**。它的 `.git` 是一个指向原仓库管理
  目录的绝对路径，原样复制后，副本里的 Git 命令会改动原工作区的索引和分支
  状态。反过来也一样：主仓库若拥有链接式 worktree，它的 `.git/worktrees/`
  里记录着那些外部工作区的路径，复制后副本会认为这些分支仍在原路径检出，
  在副本里执行 worktree 修复还可能把原工作区的指针改写到副本。
  导入器属于 P1，不能等 P1a 的 Git 集成来兜底。规则不按情形逐个列举，而是
  统一为：**导入树内任何解析到树外的 Git 管理指针都要被发现**。这包括所选
  目录本身是链接式 worktree、所选仓库拥有链接式 worktree、树内任意深度的
  嵌套仓库是某个外部仓库的 worktree，以及指向树外的 gitdir 文件和对象库
  alternates。检查须递归整棵树，不只看根目录。发现后在能安全重定位或脱钩
  之前拒绝导入，并指出具体路径和原因；指针完全落在树内的，例如普通子模块，
  不受影响。同样的指针也存在于今天的克隆里，
  第 8 节对 World 的要求不变。
- **复制不能降低静态加密保护**。源项目若受 FileVault 保护，新建的专用卷必须
  具备同等的静态加密，才能把用户数据复制进去。初始化在复制任何数据之前检查
  新卷的加密状态：无法建立同等保护时拒绝导入，或在用户明确知情并确认后才
  继续，不得静默把受保护的数据复制到未加密的卷。新卷在内置磁盘上的加密行为
  尚未验证，属于 P1 的前置验证。
- **World 的位置受限**。现状允许 `fork --to` 任意路径，跨卷时用 `--copy`。
  硬上限模式下，卷外路径默认拒绝并说明原因，不创建一个不受上限保护却看起来
  受保护的 World。是否在用户习惯的路径提供入口，例如符号链接，留待技术设计评估。
- **卷外的复制型 World 需要明确的去向**。`fork --copy` 产生的卷外 World 占用的是
  别的卷，不受上限约束，也不计入 forkfs 容量。硬上限模式须在两者中明确选一：
  继续允许，但在创建时和状态里标明“不受容量上限保护、占用不计入”；或者不再
  允许，并给出迁入受管卷的办法。已有的卷外 World 不被自动迁移、删除或改标为
  受保护，状态展示须把它们与受管 World 分开列出。
- **容量选定后不能原地修改**。系统工具没有修改既有卷配额的途径，调整容量
  等于新建卷并迁移全部内容。因此初始化时须给出建议值和依据，明确告知之后
  调整的代价；P1 须至少交付一条经过验证的扩容路径，否则选错容量只能重来。
  扩容迁移的是一个活着的 store，比首次导入更危险：checkpoint、discard、回收
  和 World 内的写入可能同时在改数据库和目录树，普通的跨卷复制会把不同时刻的
  状态拼在一起。因此上面对首次导入的要求同样适用于扩容，并且更严：迁移前
  让整个 store 静止，或取得它的一致快照，包括数据库、快照、World、trash 和
  预热池；复制后按同样的保真标准核对；切换到新卷是一次原子动作，切换前旧卷
  保持完整可用，切换失败、被取消或空间不足时回滚到旧卷并清理半成品目标；
  旧卷只在新卷核对通过且用户确认后才释放。迁移期间被拒绝的操作要说明原因。
  还有一个只属于扩容的问题：**跨卷复制保不住克隆之间的空间共享**。store 里的
  快照和 World 大多共享同一批数据块，实测每个克隆只占约 100 KB；逐棵树复制到
  新卷后，每棵树都会按自己的逻辑大小重新占用空间，几十 GB 的 store 可能膨胀为
  所有树逻辑大小之和，在切换前就撑满新卷的配额甚至整个宿主磁盘，而保真核对
  只看内容和元数据，照样通过。因此扩容必须按克隆关系重建：每份独立内容只
  复制一次，其余的树在新卷上由它克隆出来再应用各自的差异，或采用等效办法。
  迁移前按这种方式估算新卷上的物理占用并与新容量、宿主剩余空间比较，不够则
  不开始；迁移后核对新卷的物理占用与旧卷相当，明显偏大视为失败，不释放旧卷。
- **存在最小容量**。现有的克隆准入检查要求 256 MiB 可用空间，实测 286 MiB 的卷
  只有约 30 MiB 可用。产品须设定最小可选容量，准入下限改为与容量相称。
- **硬上限约束的是受管卷内的占用，不是 World 里进程的全部写入**。这条边界
  要如实说明。项目里指向卷外的符号链接，无论绝对路径还是解析到卷外的相对
  路径，会让构建和 Agent 把数据写到别的卷上，不消耗配额；进程直接写卷外的
  缓存或临时目录也一样。导入时须递归找出指向卷外的符号链接并列给用户，
  由用户选择排除、保留并接受该路径不受上限保护，或中止；不静默保留后仍
  宣称整个工作空间受硬上限保护。状态展示同样不能把卷外写入计作受保护的
  占用。要限制进程写到卷外属于执行隔离的范畴，见 `world exec`，不由容量
  功能承诺。
- **“已满”的判断要留余量**。实测写入在配额的约 98.6% 处失败，仍有数 MB 显示为
  可用却写不进去；错误码与真实磁盘满相同。产品须自行区分“到达 forkfs 上限”与
  “宿主磁盘已满”，分别给出说明，不能只转述系统错误。

容量上限不等于预留空间：宿主磁盘仍可能被其他应用占满。产品须同时展示
forkfs 容量与宿主可用空间。旧的普通目录模式不被自动迁移，也不能被标为
已经具有硬配额保护。缩容、迁移和存储区域退出流程后续单独设计。

## 4. 日常使用：看得懂的状态与提醒

用户能快速看到总容量、当前占用、可用空间和是否需要采取行动。不把克隆的
逻辑大小简单相加并冒充物理占用；指标暂不可用时明确说明，不显示虚假健康状态。

初步提醒建议：

- 低于 80%：正常展示。
- 达到 80%：建议查看可清理内容。
- 达到 95%：强调空间紧张，建议尽快清理。
- 达到限制或实际空间不足：说明写入失败原因及可行的恢复步骤。

阈值待使用反馈调整。第一阶段在 CLI 使用过程中展示提醒，不承诺常驻后台
实时通知；即便用户不运行 CLI，硬容量限制仍应由底层执行。后续是否增加
菜单栏或桌面通知取决于实际需求。

## 5. 清理体验：先说明，再执行

接近容量时提供清晰的下一步，而不是只打印“请运行 GC”：

1. 预览已到期垃圾、暂不能回收的对象及原因。
2. 有可回收内容时，由用户主动启动清理，并展示进度与结果。
3. 主要占用来自活跃 World、快照或预热池时，引导用户选择不再需要的内容。
4. 没有安全清理对象时明确说明，不能暗示 GC 一定能解决。

不自动删除活跃工作，系统不为腾空间自行缩短保留期，不承诺预览字节等于
实际释放量。

**进入回收站不释放空间**。实测中 `discard` 之后可用空间不变，默认 `gc` 因保留期
也回收 0 字节，只有保留期归零的回收才真正返回空间。接近上限时产品必须说清
这一点，并提供由用户逐项确认的“立即永久删除所选内容”，明确告知不可恢复。
这是用户的显式选择，不是系统自动缩短保留期。

### 到达上限时仍能清理：P1 验收条件

Codex review 指出清理本身需要写入，可能在上限处失败。实测证实了这一点，
而且比预期严重，详见 [可行性实测](CAPACITY_QUOTA_FEASIBILITY.md)：

- 到达上限后只有删除能成功；新建、追加、克隆以及**任何形式的重命名**都失败，
  位于该卷上的元数据库无法写入，WAL 模式下连读取也失败。
- 现有 CLI 在上限处**所有命令全部失效**，包括只读的 `status` 和 `list`，
  以及 `discard` 和 `gc`；并且把原因误报为元数据库丢失，建议用户移走 store
  重建。数据库此时完好，照做会让全部快照和 World 失去索引。这个误报与配额
  无关，今天任何一次真实的磁盘写满都会触发，应作为独立缺陷优先修复。
- 释放约 8 MiB 后，全部功能恢复，数据无损。

因此 P1 的完成条件包括：

1. 到达上限后，查看状态、列出内容和清理预览仍然可用。
2. 空间不足被如实报告为空间不足。任何错误信息都不得在这种情况下建议移动、
   重建或从备份恢复 store。
3. 用户能够在上限处完成一次清理并恢复正常使用，不需要 forkfs 之外的手工操作。
   实测中只有一种手段让完整的清理流程恢复：预留一小块控制面余量，需要时
   用删除的方式释放。把元数据放在上限之外只解决了一半：数据库可以提交，但
   `discard` 仍要把树重命名进 trash，回收器仍要先重命名为 `.deleting`，而这些
   重命名发生在已写满的数据卷上，实测全部失败。所以它单独不足以让清理可用，
   只能与预留余量搭配，或搭配一条另行设计、崩溃安全、只用删除的清理路径。
   P1 技术设计须在“预留余量”和“只删除的清理路径”中至少落实一种并验证；
   元数据外置是可选的补充，其崩溃一致性尚未测试。
4. **两种“满”都要能恢复**。实测只写满了配额卷，当时容器仍有 2.7 GB 空闲，
   所以“元数据放在同容器的另一个卷”只被证明能应对配额写满。第 3 节已经说明
   宿主磁盘可能被其他应用占满；那时同容器的所有卷一起失去空间，这一手段
   很可能同样失效，而该情形尚未测试。P1 选定的控制面余量必须在配额写满和
   整个容器写满两种情况下都能完成清理并恢复；只通过其中一种不算通过。
5. 验收在真实的配额卷上进行，覆盖上述两种写满情形下写满、清理、恢复的多次
   循环，以及回收进程、前台命令和 World 内的写入同时撞上上限的情形。

Codex review 指出的约束保留为后续设计门槛：**清理预览必须真正只读**。
当前普通 store 打开可能触发恢复和写入，不能直接复用后宣称零修改；技术方案
必须解决这一点，或明确报告无法安全预览，不偷偷执行恢复。

## 6. 付费远程备份：保护重要版本

### 用户体验

用户开通付费服务后，明确选择要备份的项目或快照，看到上传进度、远端用量、
最近成功恢复点及失败原因。第一阶段以已提交快照为备份单位，不把仍在修改
的 World 默认为已备份，也不暗示所有实时修改都得到保护。

先提供手动备份与完整恢复，再增加计划备份、可配置的历史保留和配额提醒。建议优先
评估托管远端，减少配置负担；自带对象存储、团队共享及多区域策略后续再评估。

### 恢复与信任

- 能从备份恢复到新目录或新设备，不默认覆盖已有工作。
- 明确展示“可恢复的版本”，不能把上传请求成功当作备份完成。
- 备份默认不触发本地删除，恢复也不得绕过本地容量限制。
- 加密传输与存储，明确密钥管理及恢复方式；具体安全方案单独设计和 review。
- 不上传未经用户选择的数据，不用备份内容训练或进行与备份无关的处理。

### 首个付费版本（P2）的上线门槛

P2 是第一次向用户收费并接收用户数据的版本，下列要求是 P2 自身的完成条件，
不能留给 P3 或后续版本补齐：

- **恢复保真**：恢复结果要逐项核对，不只是“能下载回来”。核对范围是第 11 节
  统一定义的保真范围，包括属主、ACL 和 BSD flags，不另行缩小。核对通过才报告恢复
  成功；备份或恢复无法保留的条目和元数据逐项列出，恢复标为不完整，不能静默
  丢弃后报告成功。支持范围在购买前说明。
  **现有的本地快照清单不能充当这份核对依据**：它只记录类型、权限、大小、
  修改时间、链接数和路径，`verify` 也只比较这些字段，大小与时间相同的内容
  损坏或丢失的 xattr 都能通过。P2 的前置是一份备份清单，为每个文件记录密码学
  内容摘要以及上述承诺保留的元数据，在备份时生成并随备份保存；或者定义一种
  同等完整的比较方式。在此之前，恢复保真不能作为已满足的验收项。
  清单自身也必须可信：逐文件摘要不能证明清单完整。若远端损坏或篡改同时
  去掉一个对象和它的清单条目，按剩余条目核对仍会报告成功。因此清单须受
  完整性保护并与恢复点绑定，例如经过认证的根摘要或签名加条目总数，且独立于
  对象集合保存；清单缺失、校验不过或条目数不符时，恢复报告为无法验证，
  不报告成功。
- **加密**：传输加密与存储加密已实现并经过验证；密钥由谁持有、用户丢失
  凭证或设备后如何恢复、服务方能否读取内容，三点在购买前说明并在验收中
  演练。不允许以明文保存付费用户的快照。
- **基线保留与删除规则**：P2 出售前必须有一份确定的默认保留与到期删除规则，
  服务端按该规则执行，用户购买前可见、变更前提前通知。具体期限属于商业
  设计，本文不设定数值；P3 只增加用户可配置的保留策略与自动化管理。
- **到期/取消后的取回**：订阅到期或取消的账户，在约定保留期内仍能查看、
  下载和恢复已有备份；权益校验不得把“订阅有效”作为取回的前提。这条在
  P2 验收中用到期账户实际演练，而不是等到 P3。
- **权限与审计**：见第 11 节验收门槛中的 P2 部分。

### 付费边界

本地容量和远端备份额度分开展示。远端额度不足时暂停新上传并提示，不默认
产生超额账单或自动升级。价格、计费口径、区域选择与保留期限尚未确定。

到期或取消订阅不影响本地工作；对于仍在约定保留期内的已有备份，允许查看、
下载和恢复，但仍须具备有效的数据访问权限，不以续费作为取回数据的条件。
成员移除或权限撤销不能因“到期可取回”而被绕过。保留期及到期删除规则必须购买前
说明并提前通知，不能在本文里擅自设定自动删除期限。

## 7. 集群版：多机器统一管理

### 用户场景与首期范围

面向拥有多台开发机、Mac 节点或 Agent 执行机器的个人与团队，提供一个统一
入口，回答“机器是否在线、空间是否充足、工作空间在哪里、操作是否完成”。
首期支持同一管理域内的 macOS 节点，不因此承诺 Linux/Windows 支持。

- **节点管理**：显式加入、命名/标签、查看版本与健康状态、撤销接入。
- **统一视图**：按节点查看容量、World、快照、备份状态及最近更新时间，
  可以筛选项目与节点，不必逐台登录查看。
- **远程管理**：选择明确节点发起创建工作空间、checkpoint、备份或安全
  清理，跟踪排队、执行、成功、失败与待确认状态；不默认提供任意远程 shell。

首期（P4）只交付管理面：节点、状态、指定节点操作与任务跟踪，**不包含任何
节点间的数据传输**。由用户选择目标节点；自动调度、负载均衡和自动故障迁移
后续再评估。

**跨机器恢复属于后续的 P5**，不是 P4 的完成条件：把已提交的快照通过明确的
数据传输或备份恢复到另一节点，先检查目标容量及权限，恢复完成不自动删除
源数据。集群管理不强制所有数据上传云端；节点间传输与付费远程备份的权益
边界单独确认，不把跨机恢复默认为已购买云备份。P4 的界面不能暗示已经可以
跨节点搬运数据。

### 必须明确的边界

每个节点仍独立存储、独立执行本地硬配额。集群汇总容量只是管理视图，不能
把 A 机器的剩余空间直接用于 B 的写入，也不承诺跨机器 fork 与本地克隆同速。
同一 World 不在多台机器同时共享可写状态；实时同步、共享文件系统和冲突
合并不属于本期集群版。

管理服务或网络不可用时，已有本地工作继续；离线节点显示离线/数据过期，
不显示健康，也不能把未收到结果的远程任务判为成功或自动重复执行。重连后
应核对任务实际状态，避免重复创建或重复清理。

统一管理必须包含最基本的节点认证、访问范围控制和操作记录；不能以首期
功能少为由省略。删除、GC 等操作明确显示目标节点与对象，支持先预览，
遵守节点本地依赖和保留策略。撤销节点接入停止新的远程控制，不擦除本地数据。
复杂企业权限、SSO、跨组织管理和控制服务高可用另行规划。

### 产品形态与商业边界

“集群版”先作为独立产品形态纳入路线图。托管控制服务还是私有部署、按节点
还是按团队收费、是否与远程备份套餐组合，均待确认；目前只有远程备份明确
为付费功能，不据此直接认定所有多机管理都付费。即便组合销售，也须分别
展示节点管理权益和远端存储额度。

## 8. 内置 Git 集成与选择性产物管理

需求跟踪：[Issue #7：World 内置 Git 集成](https://github.com/forks-world/forkfs/issues/7)。
本节记录产品方向，具体实现选择与验收细节继续在该 issue 跟踪，尚未实现。

World 是任务工作区，不强制等同于 Git worktree；但检测到 Git 仓库时，
Git 集成应内置，不能把普通目录克隆误报为已经创建 Git 分支。

- 非 Git 目录继续使用普通 World，无需账号或 Git 仓库。
- Git 仓库默认通过一次 fork 创建 Git 集成 World，建立独立分支并记录
  基线 commit，不要求用户另行手动执行 worktree add。
- 已有 worktree 必须识别其管理目录关系，不能直接复制 `.git` 指针并复用
  原工作区状态。原生 worktree 或独立 Git 管理目录的选择留待技术验证。
- 存在未提交修改时，明确选择从已提交版本创建，或携带当前修改；说明
  暂存、未暂存、未跟踪与忽略文件的处理，不静默提交或丢弃用户工作。
- 未跟踪的大文件仍按 forkfs 克隆及用户声明策略处理，不因 Git 集成而遗漏。
- checkout、commit、discard、restore、GC 不得意外损坏其他 World；若共享
  refs 或对象库，必须明确共享边界。源码基线与文件系统快照分别标识，
  不能把一次 checkpoint 自动等同于 Git commit。

文件生命周期也应按用户意图管理，而不是默认给整个目录建立长期版本：

| 内容 | 职责与策略 |
| --- | --- |
| 源码 | Git 管理提交、父子关系、文本 diff 与 merge |
| 显式发布的数据、模型或交付产物 | 产物管理记录不可变版本、确切输入依赖及保留/备份策略 |
| 用户声明可重建的中间产物 | 记录输入和生成方式，内容可按明确策略回收 |
| 用户声明的缓存、临时文件 | 默认不纳入长期产物版本及自动备份，可按已批准策略清理 |
| 未分类文件 | 不自动长期版本化，也不擅自删除或上传 |

通过配置清单、CLI 或 Agent/API 声明路径、产物版本和依赖，具体接口另行
设计。不能按扩展名推断文件可丢弃；原始数据可能不可重建。版本父子关系
用于比较/合并，输入依赖用于追溯/重建，两者不能混作共同基线。

全量文件系统快照仍可用于短期隔离和恢复，但不是所有内容都应长期保留。
远程备份范围需与用户选择一致：整快照备份须明确选择并告知包含范围，
选择性产物备份则需独立完整的清单及恢复语义，不能上传整树冒充只备份产物。

计划备份（P3）是第一个“无人值守上传”的功能，因此必须遵守上表：声明为缓存
或临时文件的路径不上传，**未分类的文件同样不自动上传**。只排除已声明的缓存
是不够的，那样未分类的内容会被默认带走。选择性的计划备份因此按正向清单
工作：只上传用户明确纳入备份的路径或产物，清单之外的一律不传，并在计划的
摘要里列出有多少内容因未分类而未被保护，避免用户误以为已经全部备份。
P3 的前置条件是这份纳入清单及其恢复语义已经交付，即恢复结果明确标出哪些
路径因未纳入而缺失，不把缺失显示为损坏，也不把它显示为完整恢复。在此之前，
或用户确实需要整树时，包括想带上未分类内容时，每个计划任务须单独、显式地
选择“整快照，包含未分类、缓存与临时文件”，并在确认时展示预计占用的远端
额度；不提供对所有计划生效的全局默认开关。
完整的产物版本与依赖管理不是 P3 的前置，仍按后续阶段单独设计。

## 9. 差异查看与审阅

### 已实现的基础能力

当前 `world fs diff W1` 比较 World 与其记录的基线快照，输出新增、修改、
删除及仅元数据变化的文件；`--stat` 提供汇总。比较涉及权限、xattr 等元数据，
已有专门的 diff 测试。**文件内容并非总被比较**：大小不同直接判为修改；大小
相同时，只有修改时间不同才读取并比较内容。保持大小和修改时间不变的改写，
例如改写后还原时间戳，会被报告为未变化，`--full` 也一样。另有两类变化目前
完全不被比较：**已存在目录自身的元数据**，即目录的权限、属主、flags 和 xattr，
两侧都是目录时直接判为未变化；以及**硬链接拓扑**，即一组路径是否仍是同一个
文件，比较中不涉及链接数或 inode 分组。这些对日常速度是合理的取舍，但不足以
支撑审阅。参见 [使用说明](../README.md#world-fs-diff)
和 [CLI 实现](../cli/main.cpp)。这些是文件级变化清单，不是逐行文本 diff，
也不是任意两个版本之间的通用比较。

### 目标体验与分期

用户在 checkpoint、备份、清理或交付 Agent 工作成果前，能看懂改动，选择
需要保留的版本，并向他人提供可审阅的结果。

- **完整判定是前置**：审阅用的比较必须能保证不漏报。P1b 须提供一种完整判定
  方式，其覆盖范围就是第 11 节统一定义的保真范围，不另列一份：文件内容，大小
  相同也比较内容或可信的内容标识；文件与**目录**的权限、属主、ACL、flags 和
  xattr；符号链接目标；硬链接拓扑，即哪些路径构成同一个文件，拆开或新建
  硬链接组都算变化；稀疏文件的空洞布局。输出中标明本次使用
  的是快速判定还是完整判定；checkpoint、备份、合并前的审阅默认使用完整判定。
  完整判定暂时覆盖不到的类别必须在输出里列为“未比较”，不能沉默；下文对
  patch 导出“列出不支持的变化”的承诺，以这些变化能被检测到为前提。
- **本地优先**：支持选择两个 World / 快照进行比较，明确显示双方身份与
  基线；提供目录/文件摘要、逐行文本差异及常规文本 patch 导出。
- **展示增强**：在基础比较稳定后，再评估可视化或外部 diff 工具集成，
  不把图形界面作为首个版本的前置条件。
- **跨机器扩展**：集群版后续支持选择不同节点上的版本或远端恢复点比较，
  明确权限、数据获取范围、传输进度与成本；不能因为已有集群总览就宣称
  已能读取和比较所有节点内容，也不默认上传文件。

### 范围与可信度

差异查看默认不修改比较对象。正在被写入的 World 不保证比较期间内容固定，
应提示结果可能变化；需要可复现审阅时引导使用已提交快照。读取失败或内容
不可用必须明确呈现，不能把“未能比较”显示为“没有变化”。

二进制、大文件、符号链接及权限/xattr 变化采用适合的摘要，不强行显示文本
行差异。patch 导出首期只覆盖明确支持的文本变更，不承诺完整保存权限、
xattr、硬链接或全部文件系统语义；不支持的变化必须列出，避免误以为 patch
能够完整还原一个 World。安全合并按下一节独立交付，不因提供 diff 就宣称
已有 merge 能力；任意 patch 的自动应用不包含在 diff 导出承诺中。

本地 diff 与文本审阅属于基础功能，不要求远程订阅；跨节点查看的管理权益
待集群版方案确认，访问远端备份仍遵守数据取回原则。

## 10. Safe merge：安全汇总分支成果

### 目标体验

多个 Agent 或开发任务从同一版本创建 World 后，用户可以审阅并汇总成果，
不必手工复制文件，也不用担心合并直接覆盖原工作。safe merge 是规划中的
新能力，不是现有 diff 的隐含功能。首期支持本地、一次两个分支的显式合并，
不承诺任意数量分支自动汇总。

源码优先使用 Git 的基线、diff 和合并语义，与 [Issue #7](https://github.com/forks-world/forkfs/issues/7)
的内置集成一起设计。用户显式发布的产物按版本选择或专门策略处理，临时文件
和缓存不默认参与；不承诺对整个工作目录做通用自动合并。非 Git 内容没有
可靠版本血缘时只支持查看差异或显式选择版本，不能伪装为安全三方合并。

建议流程：**选择版本 → 查看合并预览 → 处理冲突 → 生成独立结果 World →
用户验证后采用**。本地 safe merge 归入基础功能，不依赖付费备份。

### “Safe”的产品承诺

- **有可靠共同基线**：源码以双方 Git commit 及其共同祖先进行三方比较；
  其他支持合并的内容必须有独立、可靠的版本基线。未提交工作须显式处理，
  不能用文件系统 checkpoint 代替 Git 提交，也不边写边合并。
  基线缺失、历史关系不明或存在多个无法
  判定的基线时停止并解释，不猜测，不降级成覆盖式目录同步。保留可验证的
  版本血缘是技术设计前置条件，不能假定当前记录已经足够。
- **先预览、不动原件**：预览列出可合并变更、冲突、未支持项和输入版本；
  执行绑定这些不可变输入，不因源 World 后来改变而偷偷换版本。原始 World
  和快照不被修改，合并在隔离的结果区域进行。
- **冲突不静默覆盖**：普通文本中可以可靠合并的修改自动处理；双方冲突、
  删除与修改、路径/类型冲突等交由用户选择或编辑。不默认“后写覆盖前写”，
  未解决的结果不能标为完成；若提供冲突草稿，须明确区分草稿与完成结果。
- **不能处理就说明**：二进制、数据库、大文件、符号链接、权限/xattr、
  硬链接及重命名等分别定义支持范围。无法可靠处理时标为冲突或不支持，
  不丢弃元数据、不跟随链接向结果区域外写入，也不依靠模糊猜测合并重命名。
- **结果可放弃、过程可恢复**：通过校验后才发布新的结果 World，保留输入
  与基线记录供追溯。取消、磁盘满或进程中断不破坏输入，不把半成品报告为
  成功；容量限制和 GC 对正在使用的输入、结果的保护仍需遵守。

“安全”意味着不悄悄损坏或覆盖原工作，**不保证合并后的程序逻辑正确**。
即使没有文本冲突，也应提示用户运行项目测试并审阅结果；不自动执行输入
内容携带的脚本。第一期不原地替换目标 World，不自动部署或推送合并结果。

### 分期与边界

先完成本地两分支合并闭环与故障恢复，再考虑集群节点上的成果汇总；跨节点
需先把有权限访问的不可变版本及共同基线可靠获取到执行节点，不能把远程
活跃目录直接视为稳定输入。远程传输不自动开启，耗时与空间需求须可见。

验收重点是：能合并互不冲突的修改；冲突和不支持项不误报成功；用户可以
解决冲突后得到独立结果；取消、失败和重试不改变原件。实时多人编辑、自动
业务语义冲突解决、多分支自动调度与原地应用不属于首期。

## 11. 对象存储与集群权限管理

### 产品原则与资源边界

备份进入对象存储后，权限管理必须与远程功能一起交付，不能等到企业版再补。
登录身份、数据访问权限和付费权益是三件不同的事：付款不等于有权读取所有
备份，有权恢复已有数据也不要求订阅仍有效。个人用户默认拥有独立空间，
团队以组织/项目划分资源，默认私有、默认拒绝，未经授权不可枚举他人资源。

授权对象包括项目、备份集合/恢复点、已发布产物以及集群节点。列表、搜索、
文件名、manifest、diff 内容和下载链接同样属于受保护数据，不能只保护文件
正文。首期以项目/备份集合级授权为主，不提供复杂逐文件 ACL 或跨组织共享。

### 初步角色与动作

| 角色 | 默认职责 | 不默认拥有的能力 |
| --- | --- | --- |
| 所有者/权限管理员 | 成员、角色、项目授权与服务凭证管理 | 不应因管理账单自动获得数据读取权；管理员自授权须显式且可审计 |
| 备份写入者/节点服务身份 | 向指定项目创建备份并查询自身任务状态 | 下载已有备份、删除或覆盖历史、变更权限或保留策略 |
| 恢复读取者 | 浏览获授权的备份并下载/恢复 | 上传、删除、修改保留策略或授权他人 |
| 数据维护者 | 在授权范围内管理备份保留和删除 | 管理组织成员或读取其他项目 |

个人空间创建者可同时拥有这些角色；团队场景允许拆分。具体角色名称后续可
简化，但查看内容、创建备份、恢复、删除、管理权限须为可区分的动作。
付费/账单管理员独立于数据角色；支持人员不得默认获得客户内容访问权限。

跨节点恢复按数据来源分别授权，两种来源都要求目标节点/项目的写入权：
从远程备份恢复时，检查该备份的读取权；节点间直接传输时没有备份对象，
检查的是源节点上该项目/快照的读取权。直接传输不要求用户购买或上传远程
备份，也不能借道备份权限绕过源节点的授权。远程 diff/merge 同样检查每个
输入及输出位置的权限。节点加入集群不自动获得全部项目的备份
下载或删除权限，单个节点凭证泄露的影响应被限制在其授权范围内。

### 对象存储访问与凭证

用户通过产品授权访问备份，不向所有客户端发放共享 bucket 管理密钥。存储
默认不公开，服务端逐请求验证身份、项目和动作，并在存储访问层落实对应
边界；不能仅依赖难猜的对象 ID 或客户端隐藏按钮。客户端获得的上传/下载
能力应短时、最小范围，不能任意列举或读写整个 bucket。

**恢复点完成后只增不改**。禁止删除并不等于保护历史：写入凭证若能向已有的
对象或清单位置再次写入，就能在不“删除”任何东西的情况下让旧恢复点无法恢复。
因此上传位置由服务端分配且不可复用，恢复点一经完成即不可变；写入身份只能
新增恢复点，不能替换已完成恢复点的对象或清单。凭证泄露或客户端缺陷的最坏
结果应是多出无效的新备份，而不是损坏旧备份。
要让这句话成立，还得挡住间接的破坏：远端额度有限、保留策略按数量或空间
淘汰时，被盗的写入凭证可以灌入大量垃圾恢复点，挤占额度使正常备份无法上传，
或触发自动保留把更早的有效恢复点淘汰掉，全程不需要删除或覆盖权限。因此
自动淘汰不能仅因写入者新增了恢复点就移除已完成的恢复点：受保留规则保护的
恢复点只能由具备保留或删除权限的身份、或购买前已说明的到期规则移除；单个
写入身份的新增速率和占用有上限，异常增长会暂停该身份的上传并通知所有者，
而不是继续淘汰历史。

访问凭证支持过期、轮换和撤销，不写入普通日志或备份内容。若采用签名链接
或临时存储凭证，需明确有效窗口和撤销限制；不能声称撤权可追回已下载数据，
也不能承诺所有已签发链接瞬时失效。首期不开放匿名公共分享链接。

本地文件权限与云端权限分开管理：上传不会自动把本机用户/组映射为团队
成员，恢复时不因备份内权限元数据授予额外系统权限。加密与授权也分开设计：
有密钥不应绕过服务端访问控制，拥有管理角色也不代表能解密端到端加密内容。
团队密钥分发、成员离开后的访问边界和恢复密钥流程须在开放团队备份前明确。

### 删除、撤权与审计

删除备份、缩短保留期、变更权限和导出凭证属于敏感操作，要求相应授权及
明确确认。删除权限不能绕过已约定的保留锁；长期凭证默认不给节点永久删除
能力。账户到期与成员离职是不同事件：前者遵守数据取回规则，后者停止其
后续受保护访问；正在进行的任务在关键授权点重验，不能无限沿用旧权限。

记录操作者/服务身份、项目、对象、动作、时间和结果，覆盖授权变更、备份、
恢复/下载授权、删除和失败访问；不记录明文密钥或文件正文。审计记录由受限
入口管理，普通节点和数据维护者不能随意修改或删除；保留期另行确定。

### 分阶段验收门槛

**搬运用户数据的通用要求**。首次导入、扩容迁移、备份与恢复、节点间直接传输
都是把用户数据从一处搬到另一处，适用同一套要求，不因功能不同而各自放宽：
源是稳定或不可变的；搬运绑定一份完整且受完整性保护的源清单；目的端按下面的
**保真范围**核对，核对通过才发布结果；中断
可回滚或可在产品内清理；数据离开本机时，通道须同时具备保密性、完整性保护
和对端身份认证。后续新增的搬运路径默认继承这些要求。

**目的端的物理占用也是通用要求的一部分**。保真范围管的是内容和元数据，管不到
克隆之间的空间共享；任何离开源卷的搬运都会丢掉它。导入、扩容、从备份恢复和
节点直传因此一律：清单或传输记录里保留哪些文件、哪些树互为克隆，目的端尽量
据此重建共享；做不到时，按第 3 节的保守上界预检目的端占用，把“源上占用”和
“目的端预计占用”分开告知，预计放不下则不开始。来自一个容量合法的工作空间的
备份，不应在恢复到同样容量的受管卷时才以空间不足失败而事先毫无提示。

**保真范围**只在这里定义一次，第 3 节的导入与扩容、第 6 节的备份恢复、P5 的
节点直传以及第 9 节的完整判定都引用它：条目类型，即普通文件、目录、符号链接、
FIFO、socket 和设备节点，类型不同或条目缺失都算不一致，现有跨卷复制会重建
FIFO 却在跳过 socket 和设备节点时仍返回成功，这类被跳过的条目必须列出；
文件内容；**每一种受支持条目类型自身的**权限与可执行位、属主与属组、ACL、
BSD flags、xattr 和修改时间，不只是普通文件和目录，符号链接、FIFO 等特殊条目
同样适用，读取和写入这些元数据时作用于条目本身而不跟随符号链接；修改时间的
精度不低于现有清单记录的纳秒级，因为 `make`、增量编译器和同步工具依赖它；
符号链接目标；硬链接拓扑；稀疏文件
的空洞布局。某一条路径暂时无法保留或核对其中某一类时，必须在购买或使用前说明，并
在每次结果中把受影响的条目列出、把结果标为不完整；任何一类被省略都不能报告
为成功。各节不得自行缩小这份范围。

**目的端把清单和数据当作不可信输入**。清单受完整性保护只说明它没有被改动，
不说明写它的人是善意的：凭证被盗的写入者可以提交一份合法签名的恶意清单。
恢复和接收传输时，所有路径必须落在用户选定的目标目录之内；含 `..`、绝对
路径或借助先前创建的符号链接逃出目标目录的条目一律拒绝，硬链接目标同样受此
约束；创建过程逐级相对于已验证的目录进行且不跟随符号链接。来自其他机器的
setuid、setgid 位和设备节点不按原值创建，列为未还原。任何一次逃逸企图都使
整次恢复失败并记入审计，而不是跳过该条目后继续。P2 的恢复验收须包含一次
路径逃逸尝试，P5 的直传验收同样如此。

**属主与 ACL 在跨机器时不能照搬**。同一台机器内的导入和扩容，账户体系不变，
属主、属组和 ACL 按原值保留。恢复到另一台设备或节点间传输时，同一个 UID、GID
或 ACL 主体在目标机器上可能是另一个人，照原值写入会把恢复出的数据授权给无关
账户，这与“恢复时不因备份内权限元数据授予额外系统权限”相悖。跨机器的搬运
因此须记录源端主体，并按一份经过认证的主体映射写入目标；没有映射或映射不
确定时采用安全的回退，即归属执行恢复的用户、不授予任何其他本地主体访问权，
并把该恢复标为属主、属组、ACL 及其相关的权限含义未按原值还原，不报告为完整
成功。数字 ID 相同不构成映射依据。
回退时只改属主、去掉 ACL 还不够：保真范围要求保留权限位，而 `0644`、`0660`
里的属组位和其他人位在目标机器上指向的是另一批账户。回退因此在恢复结果的
根目录上收口：根目录归执行恢复的用户且只有属主可进入，树内各条目的权限位
按原值保留，使可执行位和工具依赖的模式不被破坏，同时目标机器上的其他账户
无法到达其中任何条目。属组设为执行恢复用户的主属组，不沿用源端的数字 GID。
恢复报告写明这一处理，并提示用户：放开根目录之前应先确认树内的属组位和
其他人位在这台机器上意味着什么。

验收门槛随功能所在阶段生效，不要求某阶段验证它尚未交付的工作流：

- **P2 付费备份**：恶意清单的路径逃逸被拒且不写出目标目录之外、写入者灌入
  大量恢复点不能挤掉或淘汰已完成的恢复点、跨租户/项目越权被拒、列表与内容权限一致、写入身份不能
  删历史也不能覆盖已完成恢复点的对象或清单、凭证过期/撤销、成员移除、到期仍可合法取回、保留约束及敏感操作审计。
- **P4 集群管理**：节点认证与撤销、节点凭证的授权范围、远程操作的权限检查
  与操作记录；控制通道加密且双向认证，命令、状态和元数据不以明文经过局域网
  或互联网，仅有身份认证而明文传输不算通过。
- **P5 跨节点工作流**：上述按来源区分的双向授权，即源读取权与目标写入权，
  分别覆盖从备份恢复和节点间直接传输；数据通道满足同样的加密要求。节点间
  直接传输不经过 P2 的备份清单，因此须自带一份完整的源清单，目的端核对内容
  与受支持的元数据后才发布恢复出的 World，不能只凭传输完成就报告成功。

SSO、复杂自定义角色、审批流及企业合规认证后续
评估，不影响首期必须具备的隔离和基本访问控制。本文只规定产品要求，
具体对象存储供应商、IAM 和密钥方案留待独立安全设计与 review。

## 12. 关键假设与验证顺序

下列假设决定对应阶段能否按本文交付。每一项先验证再实现；不成立时回到产品
层面重新决定，不在实现里悄悄换方案。

| 假设 | 状态 | 如何验证 | 不成立时 |
| --- | --- | --- | --- |
| APFS 卷配额能作为硬上限 | 磁盘映像内已实测成立 | 见可行性实测 | 不适用 |
| 普通用户能在内置磁盘容器上建立配额卷，删除后空间如期返回 | **未验证** | 在一台可承担风险的机器上按实测脚本重做，含 Time Machine 本地快照 | 与用户讨论软上限或需要管理员授权的初始化 |
| 上限处可以在产品内完成清理 | 预留余量在配额写满时实测能恢复完整清理流程；元数据外置只保证数据库可提交，重命名仍失败，单独不够；**整个容器写满的情形未测**；尚未实现 | P1 技术设计落实预留余量或只删除的清理路径，在配额写满和容器写满两种情形下做多轮写满与恢复测试 | P1 不能发布硬上限 |
| 跨卷复制能保留项目依赖的文件系统语义 | **未验证** | 对含硬链接、ACL、flags、xattr、稀疏文件的样本做导入前后核对 | 列出不支持项，中止或标为不完整 |
| 专用卷能保持与源项目同等的静态加密 | **未验证** | 在启用 FileVault 的内置磁盘上检查新建卷的加密状态与密钥归属 | 导入前拒绝或要求用户明确确认，不静默复制 |
| 备份清单足以核对恢复保真 | **不成立**：现有清单无内容摘要、xattr 和符号链接目标 | P2 技术设计定义含内容摘要与元数据的备份清单 | P2 不能宣称恢复经过校验 |
| 存在用户可接受且安全的扩容路径 | 未验证；已知无法原地修改配额 | 技术设计调查受支持的途径，否则设计迁移式扩容：静止或一致快照、按克隆关系重建以保住空间共享、保真核对、物理占用核对、原子切换与回滚，并测量耗时与所需的额外空间 | 初始化时更强地引导容量选择，并如实说明 |
| 清理预览可以真正只读 | 未验证；现有 store 打开会执行恢复与写入 | 技术设计提供只读打开路径 | 明确报告无法安全预览，不偷偷执行恢复 |
| Git 集成的工作区布局不损坏其他 World | 未验证 | 在 Issue #7 中验证 | 见 Issue #7 |
| 现有版本记录足以支撑 safe merge 的共同基线 | 未验证 | P1c 技术设计前置审计 | 只提供差异查看与显式选择版本 |

验证顺序按上表自上而下：内置磁盘验证最先，因为它决定 P1 的形态。

## 13. 交付阶段与完成标准

| 阶段 | 核心范围 | 完成标准 |
| --- | --- | --- |
| P1 本地容量闭环 | 内置磁盘上的硬上限验证、初始化硬容量与首次导入、状态、提醒、安全 GC 引导、上限处的清理、一条可回滚的扩容路径 | 用户可以设定边界、看懂占用；配额写满与宿主容器写满时状态均仍可读、错误如实、能在产品内完成清理并恢复；不出现建议移走 store 的误报；受 FileVault 保护的项目不会被静默复制到未加密的卷；首次导入来自稳定的源并经过保真核对，中断或空间不足的导入可在产品内回滚或清理重试，不越过挂载点复制外部数据，导入期间源发生变化时重做或拒绝，无法保留的条目被列出而非静默丢失；树内任意深度解析到树外的 Git 管理指针被识别并拒绝或安全处理；指向卷外的符号链接被列出并由用户决定，不把卷外写入宣称为受上限保护 |
| P1a 内置 Git 集成 | 仓库识别、独立分支、基线与修改处理；[Issue #7](https://github.com/forks-world/forkfs/issues/7) | 一次 fork 获得明确 Git 身份，不误用原 worktree，不损坏用户修改或其他 World |
| P1b 本地差异审阅 | 完整内容判定、任意 World/快照对比、逐行文本 diff、文本 patch 导出 | 用户能识别改动并导出支持范围内的审阅结果；保持大小与修改时间的改写、目录元数据变化和硬链接拓扑变化不被漏报；无法比较的内容不误报一致 |
| P1c 本地 safe merge | 共同基线、合并预览、冲突处理、独立结果 World | 不修改输入，冲突不误报成功，失败可恢复；用户验证后再采用结果 |
| P2 付费备份 MVP | 显式启用、手动备份与恢复、传输与存储加密及密钥恢复、基线保留与删除规则、权益校验、租户/项目隔离、基础角色及审计 | 完成恢复闭环，恢复结果的内容与受支持的元数据同受完整性保护的备份清单核对一致，清单缺失或被改动时报告无法验证，不支持的条目被列出而非静默丢弃；加密与密钥恢复经过演练；到期/取消账户在保留期内可取回；保留规则购买前可见且被执行；通过越权、撤权验证 |
| P3 日常备份体验 | 计划备份、正向纳入清单与选择性备份的恢复语义、失败提示、可配置保留策略、额度管理 | 用户能持续了解保护状态；计划任务只上传用户明确纳入的内容，未分类与声明排除的内容都不上传，除非该计划显式选择整快照；不会意外收费或失去取回渠道 |
| P4 集群管理 MVP | 节点接入、统一视图、指定节点操作、基础权限与操作记录、加密且双向认证的控制通道；不含节点间数据传输 | 至少两台机器可统一管理，断连/重连时状态可信且不重复执行操作；控制流量不以明文传输 |
| P5 跨节点工作流 | 快照分发/恢复、跨节点比较与成果合并、容量检查及传输状态 | 用户能比较、恢复或合并选定不可变版本，不覆盖已有工作或删除源数据；通过按来源区分的跨节点双向授权验证；传输通道加密，直接传输的结果经源清单核对内容与元数据后才发布 |

以上是建议顺序，暂不承诺日期。集群统一视图与管理本身不依赖付费备份，
可根据多机需求优先级提前；跨节点工作流可复用后续快照传输/恢复能力。
Git 集成、本地差异审阅和 safe merge 不依赖备份或集群服务，可作为独立迭代；
源码 safe merge 以内置 Git 集成和差异审阅为前置。产物版本与依赖声明在
选择性备份和跨节点产物分发前单独设计验收，可视化展示另行排期。
每阶段先有独立技术设计与验收，再开始实现；不把 P1 的本地功能依赖于账号、
支付或远程服务上线。

暂不纳入：自动淘汰用户工作、实时云同步、实时多人协同编辑、跨平台完整支持、
复杂企业权限体系、存量数据无感迁移、分布式共享文件系统和自动任务调度。
远程备份与集群的基础访问控制、租户隔离和审计不在排除范围，也不能推迟到
企业版。后续基于用户需求再排优先级。

## 14. 下一轮需要确认的事项

- 是否接受硬上限已确定的代价：专用卷、首次导入完整复制、World 只能位于卷内、
  容量选定后调整等于迁移。
- 是否同意把“磁盘写满时误报元数据库丢失”作为独立缺陷，先于 P1 其余工作修复。
- 硬上限模式下是否继续允许 `fork --copy` 到卷外，还是只保留受管卷内的 World。
- 是否认可以本地闭环 → 手动付费备份与恢复 → 计划备份的顺序交付。
- 远程服务是否优先托管，而非先支持用户自带 bucket。
- 集群版是否需要优先于计划备份；首先服务个人多机还是团队共享节点。
- 集群控制服务的托管/私有部署选择，以及独立收费或套餐组合方式。
- 本地差异审阅与容量管理的优先级，以及是否先完成 CLI 再做可视化。
- safe merge 是否按本地两分支、独立结果 World 优先交付，原地应用后续再评估。
- Git 集成与产物管理的职责边界；具体 Git 工作区布局继续在 Issue #7 验证。
- 远程权限是否以项目/备份集合为首期粒度，以及团队角色与密钥管理的范围。
- 套餐、价格、远端额度、保留期和具体技术路线另开设计，不在本轮定死。

已确认方向：硬上限优先，且磁盘映像内的实测表明它可行；安全预览不能改数据；远程备份属于付费功能；
增加集群版，支持多机器统一管理；在已有文件级 diff 上补齐差异审阅与
safe merge，明确它们尚未实现的部分和安全边界。
内置 Git 集成按 [Issue #7](https://github.com/forks-world/forkfs/issues/7) 跟踪，
源码版本与用户显式声明的产物版本分开管理。
远程备份与集群必须同时具备基础权限管理，不能只提供存储上传能力。
本轮只 review 产品范围和优先级，不代表底层能力已验证或已批准实现方案。
