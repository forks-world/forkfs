# 容量预算与 GC 引导：产品设计草案

状态：待用户 review。本文所有新命令、字段、默认值都是提案，尚未实现。
本 PR 仅包含设计，不创建卷、不设置配额、不执行 GC，也不改变现有行为。

## 1. 用户体验与本期范围

用户第一次使用时设置容量预算，日常能回答三个问题：已经用了多少、
是否需要清理、下一步怎么安全地清理。接近预算时主动提示，但不自动删除工作。

推荐第一期采用 **store 级逻辑容量预算**，而不是宣称有硬物理配额：

- `init` 时可以设置预算；旧 store 默认不设置，保持兼容。
- 展示逻辑用量、预算比例、宿主卷真实剩余空间及数据采样时间。
- 默认在 80% 提醒、95% 强提醒、100% 标记超预算；预算本身不阻断操作。
- 给出检查垃圾、清理到期垃圾、选择不再需要的对象等具体步骤。
- 不自动 discard 活跃 World/快照，不改变 retention，不自动 drain pool。

不在本期：菜单栏 UI、系统推送、常驻后台容量监控、自动删除策略、
独立 APFS 卷管理及任意外部进程写入的硬限制。

## 2. 为什么先做预算，而不是硬容量上限

当前 World 是普通 APFS 目录，可以位于 store 之外，程序直接读写目录，
forkfs 不在数据路径上。现有 `wfs_store_status()` 展示卷容量与剩余空间，
并用 entry 数估算克隆元数据成本；这不是可用于容量扣账的物理用量。
参见 [core API](../core/include/worldfs/worldfs.h)、
[store 状态实现](../core/src/store.cpp) 和 [CLI](../cli/main.cpp)。

不能用“初始化时卷空闲量减去现在空闲量”计算 forkfs 用量：其他应用写入、
删除文件都会改变结果。也不能把各目录块数之和称为精确独占物理空间：
APFS 克隆共享数据块，删除一个副本不一定释放这些数据块。

因此本提案明确取舍：预算衡量用户管理的数据规模，不代表预留磁盘空间、
精确物理占用或预计可回收字节数。若产品要求“所有 World 合计最多占 100 GiB
物理空间，达到后任何进程都不能写入”，应改为第二种产品模式：专用受限
APFS 存储域，所有受管 World 必须留在该域；需单独验证卷管理、权限、
跨卷导入、挂载恢复、迁移及退出流程，不能仅靠 CLI 检查实现。

## 3. 提议的命令与首次使用流程

```bash
# 原有 init 仍然创建初始快照，增加可选的 store 级预算
world fs init ~/src/myproj --capacity 100GiB

# 查看或调整现有 store 的预算，不必重新 init / 创建快照
world fs capacity
world fs capacity set 200GiB
world fs capacity disable

# 查看缓存；主动刷新才能得到最新逻辑用量
world fs status
world fs status --refresh
world fs status --json

# 清理前先看计划，确认后使用现有 GC 流程
world fs gc --dry-run
world fs gc
world fs gc --status
```

规则：

- 参数接受正整数加 `MiB/GiB/TiB`（二进制）或 `MB/GB/TB`（十进制），
  拒绝裸数字、负数、零、小数、未知单位和字节数溢出。禁用必须显式使用 disable。
- 预算作用于 `--store` 选定的整个 store，不是单个项目或当前快照。
- 新 store 未指定容量时保持未配置，不读取 stdin；交互与脚本行为一致。
- 已有预算时，`init --capacity` 只接受相同值；不同值拒绝并提示 capacity set，
  必须在创建快照前完成此检查，不悄悄覆盖多个项目共用的预算。
- 降低预算至当前用量以下允许，但显示超预算警告；不删除对象。
- 参数校验在创建 store 前完成。首次 init 失败不提交新预算；已有预算保持不变。
  实现需解决快照发布与预算配置的一致性，不能留下成功输出但配置未保存的结果。
- 文案中的命令带上正确的 store 参数并进行 shell quoting；不执行复制出的命令。

## 4. 统计口径与可信度

预算分子定义为 **受管对象的逻辑字节之和**：

| 对象 | 纳入预算的内容 |
| --- | --- |
| ACTIVE 快照、World | 每个对象树的文件逻辑大小 |
| pool | 已完成但尚未分配的树，单独列出 |
| trash / deleting | 尚未实际删除的内容；discard 不立即减少用量 |
| 未完成创建、遗留临时树 | 能确认归属的内容，单独列为 pending cleanup |
| DB、日志及其他 store 管理文件 | 可安全枚举的文件逻辑大小，单独列为 overhead |

普通文件采用 `st_size`；符号链接计链接本身且不跟随；目录大小不计入。
单个对象内以 `(device, inode)` 去重硬链接；不同对象分别计费，包括克隆。
这意味着 10 GiB 的完整快照再 fork 一个 World，逻辑预算可增加约 10 GiB，
即便物理磁盘只增加少量元数据。该区别必须出现在首次设置预算和状态帮助中。
原始导入目录不计费，除非它本身也是此 store 登记的受管对象。

扫描仅针对已验证身份的受管根；不追随 symlink，不扫描任意旁观目录。
快照扫描通过现有受保护访问机制，不永久修改 gate/immutable 权限。
嵌套根、重复归属、移动后身份不匹配不得盲目重复累计：标记为不完整并引导 verify。
未知 orphan 不自动归属、不自动删除，单独报告异常。

扫描并非原子快照：并发写入可能使结果近似。每次结果记录起止时间、覆盖对象数、
错误数和完整性；权限错误、离线卷、路径消失、并发创建/删除引起覆盖变化时，
显示 `partial`，不能将未读到的对象视为零或给出“容量正常”的结论。
对象的字节累加必须检查溢出。

另外展示 store 所在卷及外置 World 所在卷的可用空间；按文件系统身份去重，
不把不同卷的剩余空间相加。真实磁盘低空间与预算告警是独立信号，优先展示
真实低空间；既有 P11 admission check 和真实 ENOSPC 错误处理保持有效。

## 5. 状态、提醒与性能

| 比例（完整且新鲜的样本） | 状态 | 用户提示 |
| --- | --- | --- |
| < 80% | ok | 用量摘要 |
| >= 80% 且 < 95% | warning | 建议检查 GC 计划 |
| >= 95% 且 < 100% | critical | 强调接近预算，列出安全清理步骤 |
| >= 100% | exceeded | 已超预算，建议清理或调整预算；仍允许操作 |
| 未配置 / 无有效样本 | disabled / unknown | 不生成虚假的百分比或健康结论 |

默认缓存有效期 5 分钟。过期显示 `stale`，不凭旧的低用量撤销已有告警。
CLI 生命周期操作后标记样本 dirty；外部直接写入不能可靠立即感知，因此即使
缓存未过期也显示采样时间。完整刷新后才清除告警，不以 GC 请求成功为依据。

`status --refresh` 显式扫描；普通 status 和 init/fork/checkpoint/discard/restore/
pool/gc 完成后只读取缓存和廉价卷空间信息，不把全树扫描加入 fork 热路径。
无缓存或 dirty 时提示刷新，不假装已完成即时用量统计。
第一期不承诺“用户仅在外部编辑、完全不再运行 CLI 时仍会收到提醒”。

提示写 stderr，不污染已有 ID 等 stdout 输出；成功命令的退出码不因软预算
警告改变。扫描失败时显式 refresh 返回非零，但输出可读的部分结果；JSON
包含 budget_bytes、logical_bytes、ratio（未知时 null）、severity、freshness、
complete、sample 时间、分组用量、各卷空间和建议动作，避免脚本解析人类文案。
单次命令只打印一次容量提醒；显式 status 始终展示状态，不做跨进程静默节流。

示例（提议文案）：

```text
capacity: 83 GiB / 100 GiB logical (83%, warning)
sample:   complete, sampled 2 minutes ago
volume:   214 GiB available on store volume
note:     shared clone data is counted per object; this is not physical usage
next:     world fs gc --dry-run
```

## 6. GC 引导与数据安全

`gc --dry-run` 是新能力：只列当前 retention 下到期的垃圾、暂不能删除的对象、
worker 状态及异常项；不做 reconcile、不改变行状态、不启动 worker。
输出对象级原因及逻辑字节估算，绝不承诺回收同样数量的物理空间。
dry-run 不冻结后续状态，实际 GC 必须重新检查资格、锁和身份。

建议动作按实际状态生成：

1. 有到期垃圾：建议现有 `gc`；worker 已运行则提示 `gc --status`。
2. 垃圾尚在 retention 内：说明何时到期，不默认建议缩短 retention。
3. pool 占用明显：展示可选的 `pool drain S<n>`，说明会影响 fork 延迟。
4. 主要是活跃对象：引导 list/inspect，用户自行选择 discard；快照依赖限制照旧。
5. 没有可清理对象：明确 GC 无法解决，建议调整预算或管理其他磁盘内容。

不因接近容量而调用自动 discard、强制 GC 或修改 retention。后台 GC 已有的
行为保持原样，预算通知不增加自动破坏性动作。清理失败、权限错误和重试上限
应继续呈现，不得显示“已释放”；释放量只能标为观察到的卷空闲变化，且可能
受其他进程影响，不能等同于 forkfs 独占回收量。

## 7. 数据模型与实现拆分

- 配置持久化到现有 SQLite meta：容量字节数、统计模式和配置版本。
  缺省表示 disabled。读取到损坏/未知配置时显式报错，不悄悄恢复默认预算。
- 配置事务写入；并发 init 不可互相覆盖。初始化成功边界须有故障注入测试。
- 新增独立容量查询 API/结构体，不改写现有 metadata estimate 字段的含义。
- 样本独立存储，可丢弃并重建，包含配置版本及对象清单版本；过期扫描不能覆盖
  更新配置对应的样本。扫描期间不长期持有全局 store mutex/SQLite 写事务。
- 能复用已有只读枚举、身份检查和 GC 资格判断的地方共享逻辑，避免 dry-run
  和实际 GC 对“可删除”产生两套互相矛盾的判断。
- 旧版本忽略新增预算只会失去提醒，不绕过硬安全限制；若实现引入新的生命周期
  状态/表约束，再按现有 schema 迁移规则独立评估，不能无依据改版本。

交付顺序：配置与命令解析 → 安全统计与状态输出 → 轻量提醒 → GC dry-run/
建议动作 → 文档及端到端验收。每一步均保留无预算旧 store 的原有行为。

## 8. 验收与回归测试计划

- 参数：单位、边界、零/负数/小数/溢出；错误输入不创建 store。
- 配置：首次 init、失败回滚、重开持久化、重复 init、并发冲突、set/disable、
  未配置旧 store 与损坏配置。
- 统计：APFS 克隆分别计费、对象内硬链接去重、稀疏文件、符号链接、gate、
  外置 World、pool/trash/deleting/残留树、管理文件、重复根及归属不明。
- 可靠性：权限/IO 错误、移动或卸载、扫描时增删对象、采样取消、字节溢出；
  partial/unknown/stale 不得输出健康结论。
- 提醒：精确覆盖 80%/95%/100% 两侧边界，预算与真实低空间同时发生，
  stdout/退出码兼容，正确 store 的可复制命令，无人值守不阻塞。
- GC：dry-run 零写入且不启动 worker，retention/依赖/锁约束一致；计划与执行
  之间发生变化仍安全；没有可清理内容时不误导；GC 后显式刷新恢复状态。
- 性能：固定已有 pool-hit 基准对比提醒开关；确认 fork 路径无递归扫描；大树
  refresh 测量耗时/内存并支持中断，不承诺未经测量的固定延迟。
- 集成：现有 CTest、安全测试及真实 ENOSPC 回归保持通过，新增 CLI 测试进入 CI。

## 9. 请优先 review 的产品决策

1. **预算还是硬配额？** 推荐本期预算。如果“总容量”必须指独占物理容量，
   则需要改为受限存储域方案，不能沿用本期统计口径。
2. **是否接受克隆重复计入逻辑预算？** 这是可解释、可测试的口径，但可能在
   物理空间仍充足时很快提醒；若不接受，应先解决物理存储域设计再实现。
3. **默认 80%/95% 提醒、100% 不阻断是否合适？** 本期固定阈值，避免增加
   配置项；后续可按使用反馈扩展。
4. **是否接受 CLI 触发提醒 + 显式刷新？** 如需持续实时提醒，应新增监控产品
   需求、功耗/性能预算及进程生命周期设计。
5. **是否保持用户主动删除？** 推荐只引导现有安全 GC，不自动牺牲历史或 World。

以上决策确认后再开实现 PR；本文不视作用户已批准默认方案。
