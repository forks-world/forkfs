# APFS 卷配额作为硬容量上限：可行性实测

本文是 [产品规划](CAPACITY_MANAGEMENT_DESIGN.md) 第 3、5 节的证据，回答 PR #6 上的问题：
“能实现物理上限么？不行再考虑软上限。”它记录观察到的事实，不是实现方案。

## 结论

在本次测试范围内，**APFS 卷配额可以作为物理硬上限**：由文件系统执行，不依赖 forkfs
进程在运行；按物理字节计费，克隆几乎不占配额。它同时带来四个必须由产品承担的后果：
首次导入是整树复制；容量创建后不能原地修改；到达上限时只有删除能成功；现有 CLI 在
上限处全部失效并给出危险的建议。内置磁盘容器上的行为尚未验证，见文末。

## 测试环境与范围

macOS 27.0 (26A428)，arm64，普通用户，全程未使用 sudo。所有卷操作都在测试自建的 3 GiB
稀疏 APFS 磁盘映像容器内完成，每次 `diskutil` 变更前确认目标为 `Virtual: Yes` 的映像设备，
没有触碰内置磁盘。被测 CLI 为 `build/ci/cli/world`（`WFS_FSKIT=OFF`）。测试结束后映像已
卸载，临时目录已删除。字节阈值是这一配置下的观察值，不是 APFS 常数。

## 观察到的事实

### 配额的创建与呈现

- `diskutil apfs addVolume <container> APFS <name> -quota 300m` 以普通用户身份成功，无提示。
  配额为 300,003,328 字节；20 MB 的配额同样有效；卸载后重新挂载，配额不变。
- `statvfs` 与 `df` 把配额报告为卷的总大小，`world fs status` 因而直接显示配额。
- 配额是上限，不预占空间。`-reserve` 相反：立即计入，并减少同容器其他卷的可用空间。
- 新卷自动挂载在 `/Volumes/<name>`，归调用者所有且可写；`diskutil mount -mountPoint`
  可由普通用户把它挂到任意目录。
- **`diskutil apfs` 没有任何修改既有卷配额的子命令**；`eraseVolume` 的手册明确说明不继承
  配额。改变容量意味着删除并重建卷。是否存在私有 API 未调查。

### 执行

- 写入在 295,698,432 字节处失败，即配额的 98.57%。此时容器仍有 2.7 GB 未分配，同容器的
  另一个卷成功写入 200 MB，说明生效的是配额而不是映像大小。
- 错误码是 **`ENOSPC`，从不出现 `EDQUOT`**，与真实磁盘满无法从错误码区分。
- 约 3.4 至 4.2 MB 被 `statvfs` 报告为可用，但任何方式都写不进去。
  “可用字节大于零”不能推出“写入会成功”。

### 克隆计费

| 步骤 | 已用字节 | 增量 |
| --- | ---: | ---: |
| 103 MiB 的树（300 个文件） | 108,298,240 | |
| 第 1 次整树克隆 | 108,396,544 | +98,304 |
| 第 5 次整树克隆 | 108,814,336 | 每次约 +100 KB |
| 在一个克隆里重写 10,752,000 字节 | 119,627,776 | +10,813,440 |

配额按物理字节计费：克隆只付目录与 inode 元数据，分叉的内容在分叉时计费。

### 跨卷

同一容器内两个卷之间的 `clonefile(2)` 对文件和目录都返回 `EXDEV`。`cp -cR` 跨卷时返回
成功，但悄悄退化为逐字节复制。因此把项目首次导入配额卷必然是一次完整复制，
其大小计入配额。

### 到达上限时哪些操作还能成功

| 操作 | 结果 |
| --- | --- |
| `unlink` 小文件、20 MiB 文件，递归 `unlink` 加 `rmdir` | 成功，空间立即返回 |
| `mkdir`、`open(O_CREAT)`、追加 4 KiB、`clonefile` | 失败，`ENOSPC` |
| `rename`：同目录改名、跨目录移动、目录或文件 | 全部失败，`ENOSPC` |
| SQLite 写入，数据库在配额卷上，全部六种 journal 模式 | 失败，`SQLITE_CANTOPEN` 或 `SQLITE_FULL` |
| SQLite 只读查询，数据库在配额卷上，WAL 模式 | **失败**，`SQLITE_IOERR_SHMOPEN` |
| SQLite 只读查询，非 WAL 模式 | 成功 |
| SQLite 写入，数据库在同容器的另一个卷上 | 成功，三次重复均成功 |

也就是说，在上限处只有删除可行。forkfs 的 `discard` 是一次进 trash 的 `rename`，回收器
删除前先 `rename` 成 `<name>.deleting`，两者在上限处都被挡住；只用 `unlink` 和 `rmdir`
的清理路径则能推进。

测试了两种缓解手段，它们解决的范围不同：

- **预留余量**：空间充足时建一个 8 MiB 的占位文件，到达上限后 `unlink` 它，上表中所有失败
  的操作第一次重试即成功。占位文件必须用 `unlink` 释放，对它 `rename` 同样失败。
- **元数据放在上限之外**：数据库位于同容器的另一个卷时，配额卷写满不影响提交。两个卷
  之间的崩溃一致性没有测试。这只证明它能应对配额写满；测试时容器仍有空闲空间，
  整个容器写满的情形没有覆盖。**它只证明数据库能提交，不证明清理能完成**：
  `discard` 与回收器的重命名仍发生在写满的数据卷上，按上表会失败。单独使用它
  不能让现有清理流程恢复，需要搭配预留余量，或一条只用 `unlink` 和 `rmdir`
  且崩溃安全的清理路径；后者尚不存在。

### 真实 CLI 的端到端表现

store 与项目都放在 286 MiB 的配额卷上，空间充足时 `init`、`fork`、`checkpoint`、`status`
工作正常。

- **准入下限吃掉小配额**：`kSpaceFloor` 为 256 MiB，可用空间低于它时 `fork`、`checkpoint`、
  `pool fill` 以退出码 3 拒绝，所以这个卷只有约 30 MiB 可用。`fork` 有 `--skip-space-check`，
  另外两个没有。
- **到达上限后所有命令失效，且建议危险**：从 World 内部把卷写满后，`status`、`list`、
  `diff --stat`、`inspect`、`verify`、`discard`、`restore`、`gc --status`、`gc --now`、
  `gc --reconcile` 全部以退出码 3 失败，并输出同一条信息：

  ```
  world: the store at ... still holds trees ... but its metadata3.db is missing or unreadable.
    try: restore metadata3.db from a backup, or move the directory aside
         (`mv <store> <store>.damaged`) and start a new store
  ```

  此时 40,960 字节的 `metadata3.db` 完好无损。原因是 store 数据库使用 WAL 模式，上限处无法
  建立 `-shm` 映射，连只读打开也失败，而 CLI 把它诊断为数据库丢失。照这条建议操作会让
  所有快照和 World 失去索引，而真实情况只是暂时没有空间。**这个缺陷与配额无关，任何
  真实的磁盘写满都会触发。**
- **释放几 MB 即可完全恢复**：删除一个 8 MiB 文件后，所有命令恢复正常，没有数据丢失。
- **`discard` 与默认 `gc` 不释放空间**：`discard` 之后可用空间不变；`gc --now` 因保留期
  删除 0 个对象；`gc --now --retention 0` 才把约 285 MiB 全部收回，幸存的快照与 World 完好。

### 其他

- `fseventsd` 在新卷上写入约 40 KB 的日志，计入配额。
- 磁盘映像内的卷默认关闭 Spotlight，并以 `noowners` 挂载；这两点是映像的属性。

## 尚未确立

- **内置磁盘容器上的一切**。按安全规则没有在内置容器上尝试 `addVolume`。普通用户能否添加
  卷、是否弹出认证、FileVault 与卷组规则是否干扰，均未知；手册只说“需要拥有受影响的磁盘”。
- **被删除的文件仍被打开时的空间返回**。“`unlink` 后空间立即返回”是在没有
  进程打开这些文件时观察到的。文件被删除而描述符未关闭时，数据块要到最后一个
  描述符关闭才释放；World 里仍在运行的 Agent 或构建会造成这种情形，本次没有
  测试。只靠删除的清理因此不能以“删除成功”推断“空间已返回”。
- **整个容器写满时的行为**。本次只写满了配额卷，容器当时仍有 2.7 GB 空闲。
  宿主磁盘被其他应用占满时，同容器的所有卷一起失去空间；“元数据放在同容器的
  另一个卷”在那种情形下很可能同样无法写入，预留余量是否仍然有效也未知。
- **新建卷的静态加密状态**。源项目受 FileVault 保护时，新建的配额卷是否加密、
  使用谁的密钥，没有测试。首次导入是完整复制，若新卷未加密，会降低数据的
  静态保护。
- **Time Machine 本地快照是否会钉住已删除的字节**。这是“删除后空间立即返回”在真实内置
  磁盘上最可能不成立的情形。
- Spotlight 在内置容器的卷上是否持续消耗配额；启用 owners 时的 uid/gid 行为。
- 多个进程同时撞上 `ENOSPC` 时的行为；所有上限测试都是单进程。
- 元数据与数据分处两个卷时的崩溃一致性。
- 样本只有一台机器、一个系统版本、一种容器类型。
